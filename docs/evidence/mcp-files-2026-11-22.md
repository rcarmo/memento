## Experimental MCP file transfers: development measurements

The adapter is opt-in and has not been deployed. It follows the files draft at [8a859b8f][draft]. Existing asset staging, accepted-asset reads and proposal approval still own storage and canonical changes.

### Profiling and allocation fixes

Measurements used Go 1.26.11 on Linux/amd64, Intel i7-12700. CPU, allocation-space and allocation-object profiles were inspected for the service metadata parser and nested uMCP protocol/HTTP benchmarks. Each before/after benchmark used the same inputs and a one-second measurement interval. Operation counts differ; comparisons below use per-operation results, not profile totals.

| Workload | Before | After |
| --- | --- | --- |
| Opt-in version check, one core | 41.62 ns; 64 B; 1 allocation | 1.511 ns; 0 B; 0 allocations |
| File metadata validation and continuation binding, four cores | 7,041 ns; 1,801 B; 36 allocations | 1,672 ns; 1,152 B; 16 allocations |
| 1 MiB loopback HTTP download, one core | 298,586 ns; 46,949 B; 94 allocations | 296,313 ns; 14,131 B; 90 allocations |

Version checks allocated a combined version slice on every request. Separate scans remove that allocation. Metadata validation cloned and sorted two maps and always constructed a rational number. Typed canonical JSON preserves field presence/order and exact numeric instance equality, with a fast path for integer sizes and bounded rational parsing for alternate numeric spellings. The metadata benchmark reduced latency by 76%, bytes by 36% and allocation count by 56%.

The streamed HTTP path allocated a 32 KiB fallback copy buffer for each response. A bounded buffer pool removes that repeated allocation and clears buffers before reuse between principals. Allocated bytes fell by 70%; the 0.8% latency change is too small to establish a latency improvement from this run. The benchmark transfers an in-memory 1 MiB payload over loopback; it excludes repository lookup and archive hashing and does not measure NAS throughput.

A separate 8 MiB ZIP check found that repeated upload confirmation allocated 16,843,840 bytes by materialising the staged BLOB twice. Reading the immutable staging write's validated SHA-256 receipt and actual stored length reduced the same confirmation workload to 42,952 bytes (99.7% less), without changing pack validation or byte-consumer checks. The final implementation also stores the completed result, so retries succeed after proposal consumption clears the staged BLOB. Its first confirmation allocated 46,192 bytes in the final check; a 1 MiB allocation ceiling guards this metadata-only operation. Fixture construction and HTTP upload buffering are outside those measurements. CPU captures for these short integration runs have limited sampling; the allocation measurements establish the result, with no latency claim.

Remaining sampled work includes JSON encoding, semver validation and HTTP parsing. The metadata path takes about 1.7 microseconds in this workload. No larger optimisation is justified by these measurements. Archive download integrity is checked before response headers, and an open descriptor pins the verified file while its bytes are streamed. Uploads retain the existing bounded ZIP-staging implementation.

### Development verification

The final root `go test -p 2 ./... -count=1` passed. Targeted service/assets race tests passed twice; the complete nested uMCP race suite passed. Vet passed for the changed packages and nested module. A three-second metadata fuzz run completed 22,827 executions without failure. A final pass also covered the CLI/service/assets packages after adding raw-connection abort handling. Tests cover both HTTP modes, short-stream aborts on both reference wire adapters, custom MCP paths, read-only configuration, capability negotiation, legacy discovery, principal/argument/state binding, expiry, invalid metadata, byte-integrity failures, current read permissions, streamed-response closure and completed-result replay after proposal consumption.

Statement coverage is 99.6% for the service package and 99.9% for the nested uMCP package in these runs; metadata parsing and the new storage-receipt methods reach 100%. Some defensive I/O/error branches are uncovered. Full release qualification needs those gaps closed and the pinned audit, cross-build, model and container matrix run. No release, push or production deployment was requested for this change.

Raw profiles, matching binaries and disposable benchmark logs were deleted immediately after analysis. Production, model assets and installed toolchains are unchanged.
